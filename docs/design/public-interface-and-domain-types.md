# 公共接口与领域结构设计

> 状态：草案（Draft）
>
> 本文档用于逐项确认设计；状态变为“已确认”前，不据此修改代码。

## 1. 目标

重新设计项目的公共接口与领域结构，使调用者能以少量、稳定的概念完成：

1. 从已经消解的农历出生资料创建命盘；
2. 读取本命盘；
3. 在不复制本命盘的前提下读取大限与流年；
4. 为未来的多语言 SDK 保留一致的领域语义。

这里的“接口”不仅指函数签名，还包括调用者必须知道的不变量、错误、顺序、能力限制和生命周期。

## 2. 设计流程

设计按以下顺序确认。前一层未确认，不进入后一层。

1. **产品接缝**：公共契约主要服务谁，各语言实现之间是什么关系；
2. **用户任务**：调用者必须完成哪些端到端任务；
3. **参照研究**：针对已确认任务研究成熟计算引擎与跨语言库的接口模式；
4. **领域模型**：确定术语、实体、值对象、关系和不变量；
5. **公共接口**：确定构造、查询、投影与错误模型；
6. **语言适配**：Rust 公共 API 稳定后，再确定各语言 SDK 的表达方式；
7. **模块结构**：根据已确认接口放置接缝与实现；
8. **实施切片**：文档整体确认后，再拆成可独立验证的纵向切片。

## 3. 当前事实

以下是对当前仓库的描述，不是目标设计。

### 3.1 Rust 核心

- `ZiweiBirth` 与 `ZiweiInput` 是经过校验后才能得到的输入类型；
- `Ziwei` 同时承担构造结果、本命真相源和全部查询入口；
- crate 根公开导出 `Branch`、`Stem`、`Palace`、`Star`、`ZiweiFly`、`DecadeStep`、`ZiweiView` 等领域类型；
- 本命、大限、流年通过 `ZiweiView` 选择器传给 `Ziwei` 的查询方法；
- 多字段结果类型字段私有，由引擎装配，通过 getter 读取。

### 3.2 语言绑定

仓库当前不包含语言绑定。TypeScript、Python、Java 和 Swift SDK 都等 Rust 公共 API 稳定后再设计与实现。

### 3.3 已确认的领域约束

重新设计可以替换现有接口，但除非明确重新讨论，不应意外改变这些领域约束：

- 调用方提供出生原始量，引擎计算命宫、宫干、局数、星位、生年四化、宫干飞化和大限；
- 本命盘是固定真相源，大限与流年只改变宫职叠落，并按叠落后的地支复用本命宫干飞化；
- 身宫叠落在十二支之一，不是第十三宫；
- 只有真实农历出生年才能支持绝对流年序号；
- 对外盘面位置使用 `Branch`，其下标为子 = 0；
- 引擎结果不能由调用方伪造为领域真相。

## 4. 当前张力

1. **Rust 公共接口尚未稳定**：当前先完成 Rust 领域模型与查询面，暂不设计跨语言契约。
2. **`Ziwei` 职责集中**：它同时提供身份信息、宫位、星位、四化、大限、流年与宫干飞化查询。需要判断这是一个足够深的模块，还是调用任务之间缺少更清晰的投影。
3. **部分接口暴露存储布局**：例如固定长度数组及“支序 × 四化序”的顺序约束。需要判断这是领域承诺还是实现细节。
4. **领域对象与传输对象尚未区分**：Rust 领域模型稳定后，再决定各语言 SDK 应使用 getter、只读快照还是更高层投影。
5. **显示信息混入公共领域面**：中文标签与领域身份类型一起导出。需要在后续决定显示元数据是否属于核心契约。

## 5. 设计原则（待整体确认）

- 不保留旧接口兼容层；新设计确认后直接替换旧路径；
- 公共接口按调用任务组织，不按内部数组或计算步骤组织；
- 引擎保持唯一排盘真相源，各语言适配器不复制规则；
- 不可能状态在进入引擎前被拒绝，计算结果保持只读且不可伪造；
- 只有真实存在第二种实现时才建立可替换接缝；
- 优先形成小接口、深实现；调用者无需理解排盘流水线；
- Rust 是当前唯一实现；未来 SDK 共享领域语义，但可以采用符合各语言习惯的表达。

## 6. 顶层决策 D1：公共契约面向谁

状态：**已确认（2026-08-05）**

### 方案 A：Rust 优先

Rust crate 是唯一权威公共接口；未来 SDK 仅按需要选择性暴露能力。

- 优点：Rust 表达最自然，实现约束最少；
- 代价：各语言 SDK 容易长期落后，跨语言语义需要人工同步。

### 方案 B：语言中立的领域契约，语言适配器各自惯用表达（建议）

先定义一套与语言无关的领域概念、任务和结果语义；各语言 SDK 提供惯用接口，但必须通过相同契约测试。

- 优点：保留 Rust 的类型能力，同时让各语言 SDK 共享同一套领域规则；
- 代价：每个设计决策都要考虑跨语言表达，不能只从 Rust 实现便利出发。

### 方案 C：可序列化快照优先

以稳定 JSON/Schema 为权威契约；Rust 与各语言 SDK 都围绕同一份命盘快照工作。

- 优点：跨语言、存储、网络传输和前端消费最直接；
- 代价：容易把所有内部数据一次性固化为公共格式，接口面较大，领域行为可能散落到调用方。

### 建议

选择 **方案 B**，但按 Rust 优先的顺序实施。先稳定 Rust 领域模型与公共 API，再设计语言绑定，避免让尚未稳定的接口过早固化到多个 SDK。

### 决定

采用 **方案 B：语言中立的领域契约，语言适配器各自惯用表达**。

由此产生以下约束：

- 领域概念、输入语义、结果语义与错误分类必须跨语言一致；
- Rust 类型与各语言 SDK 的表示不要求机械同形；
- 所有语言 SDK 必须共享同一组契约场景，不能分别演化领域功能；
- JSON、Rust 内存布局或某个绑定生成器都不是领域契约的权威来源。
- Rust 公共 API 稳定前，不实现语言绑定。

## 7. 顶层决策 D2：最小用户任务集

状态：**待确认**

### 主要调用者

第一版公共契约主要服务**命盘应用与分析模块的开发者**。他们需要可靠地排盘、浏览命盘和取得结构化领域事实；终端命理用户不是本模块的直接调用者。

### 任务 T1：创建命盘

调用者提交已经消解的农历出生事实，得到一份不可变命盘；输入不合法时得到结构化错误。调用者不负责安宫、安星、定局、四化、宫干飞化或大限计算。

是否同时保留“调用方已提供生年干支、但没有真实出生年”的原始量入口，留到输入模型阶段确认；它不能迫使后续查询分裂成两套命盘类型。

### 任务 T2：读取完整本命盘

调用者能把命盘作为一个完整的十二宫模型读取，用于渲染或分析：

- 生成命盘时使用的完整标准化出生事实；
- 生成命盘时使用的核心排盘规则集标识；
- 十二地支上的本命宫职与宫干；
- 身宫与来因宫的叠落地支，以及五行局；
- 默认十八星及其落宫；
- 生年四化。

调用者不应为了组装一张本命盘而理解内部数组下标、计算波次或逐个调用大量低层 getter。

### 任务 T3：选择并读取时间视图

调用者能：

- 浏览大限序列；
- 按大限步或虚岁定位大限；
- 在具备真实出生年时取得该大限覆盖的农历年；
- 选择本命、大限或流年时间视图；
- 读取该视图下的宫职叠落。

切换时间视图不得改变或复制本命星位、宫干、来因宫、生年四化和宫干飞化边。

### 任务 T4：读取生年四化与宫干飞化关系

调用者能取得：

- 本命盘的生年四化；
- 某地支或当前时间视图下某宫职发出的宫干飞化边；
- 每条飞边的源、四化象、被化星、目标与已保存的自化标注。

调用者不应自行重建“本命宫干 × 四化星表 × 星位”的关系。

### 第一版明确不承担

- 公历/农历换算、闰月和晚子时流派消解；
- 命理解读、批命文本或吉凶判断；
- UI 布局、主题、国际化和最终显示文案；
- 自定义星系、流派规则或插件扩展点；
- 多跳宫干飞化链、杂曜、小限；
- 持久化格式、稳定 JSON Schema 或网络传输协议；
- 批量排盘与盘内并行接口。

这些能力未来可以建立在已确认的领域契约之上，但不能扩大第一版接口。

### 用于校验任务边界的场景

1. 命盘应用从一份农历出生资料创建命盘，渲染本命十二宫，再切到某步大限和其中一个流年；切换后本命固定事实保持不变。
2. 历法模块只提供合法生年干支时，仍能创建和读取本命盘；但引擎不能假装知道真实出生年，也不能自动列出某大限对应的绝对农历年。
3. 分析模块查询“当前流年命宫发出的四条飞边”；它只表达宫职和时间视图，不自行换算地支或扫描全量边集。

### 建议

确认 T1–T4 为第一版完整任务集。它覆盖当前已实现的领域能力，但把 50 多条规则级需求收敛为四个调用任务；具体结构体和方法只有在能直接支撑这些任务时才进入公共接口。

## 8. 顶层验收标准（初稿）

最终设计至少应让调用者在不了解内部排盘流水线和数组布局的情况下：

- 用合法出生资料创建命盘，并得到结构化输入错误；
- 遍历十二宫，读取宫职、宫干、星曜和身宫叠落；
- 选择一个大限或流年，读取该视图下的宫职叠落，并使用对应地支的本命宫干飞化；
- 读取本命宫干飞化边及已保存的自化标注；
- 明确知道某项查询是否需要真实出生年；
- 未来的语言 SDK 能获得相同结果语义；
- 通过公共接口测试完整行为，不依赖内部 module 或存储顺序。

## 9. 与现有 ADR 的关系

- ADR-0001、0002、0003、0007、0008、0009 中的领域规则暂作输入约束；
- 若改变“`Ziwei` + `ZiweiView` + 查询方法”的形态，需要替代 ADR-0004；
- 若改变结果类型的封装方式，需要替代 ADR-0010，但仍需保持结果不可伪造；
- 语言绑定不再沿用旧实现；Rust 公共 API 稳定后重新设计。

不在设计过程中直接改写旧 ADR。待新设计整体确认后，再用一份新的 ADR 说明哪些旧决策被替代以及原因。
