# `ziwei_core` 排盘性能优化方案

> 状态：**评估完成，当前暂缓实施。**
>
> 本文记录 `Natal` 构造的当前基线、优化储备、触发条件和验证门槛，不是近期实施计划。文中的体积与性能收益除当前基线外均为待验证估算，不构成已经成立的实现结论。

## 目标

在保持 `ziwei_core` 领域事实、不可变结果模型和零堆分配构造的前提下，继续降低：

- 单盘构造延迟；
- `Natal` 的驻留体积和搬运成本；
- 大批量排盘时的内存带宽压力。

不在本轮方案中引入兼容层、全局缓存、查询层能力、流年盘或并发框架。

## 当前基线

基线来自提交 `59a71ad`（`perf(core): optimize natal chart construction (#294)`）及 2026-08-06 的本地测量。

环境：

- Apple M4 Max，`aarch64-apple-darwin`；
- Rust `1.97.1`，LLVM `22.1.6`；
- Criterion 每次迭代构造 60 个代表输入。

测量命令：

```bash
cargo bench -p ziwei_core --bench natal -- \
  --warm-up-time 1 --measurement-time 3 --sample-size 20 --noplot
cargo bench -p ziwei_core --bench natal_allocations
```

| 构造入口 | 60 盘耗时 | 单盘折算 | 吞吐量 |
| --- | ---: | ---: | ---: |
| `create_from_input` | 约 `14.631 µs` | 约 `244 ns` | 约 `4.10 Melem/s` |
| `create_from_birth` | 约 `14.486 µs` | 约 `241 ns` | 约 `4.14 Melem/s` |

两个入口当前都保持：

- 总堆分配次数为 `0`；
- 总堆分配字节为 `0`；
- `size_of::<Natal>() == 2188`。

当前管线已经使用定长数组、按枚举下标直接寻址和 `ArrayVec`，消除了原有的宫位星曜堆分配与重复扫描。因此，后续优化主要是固定规模数据的表示和常数成本，不再是渐进复杂度优化。

## 当前成本模型

`Natal` 的主要体积分布如下：

| 组成 | 当前体积 | 占 `Natal` 比例 |
| --- | ---: | ---: |
| `[Decade; 12]` | `1488 B` | 约 `68.0%` |
| `[Palace; 12]` | `672 B` | 约 `30.7%` |
| 其余上下文与派生字段 | `28 B` | 约 `1.3%` |

细分后：

- 每个 `DecadeYear` 为 `12 B`，一张盘固定物化 `120` 个；
- 每个 `PalaceTransformation` 为 `6 B`，一张盘固定保存 `48` 条，共 `288 B`；
- 十二个 `ArrayVec<Star, 6>` 共 `336 B`，实际十八颗 `Star` 只占 `72 B`。

排盘输入域与宫、星、四化数量均有固定上限，所以当前构造理论上已经是 `O(1)`。下面各方案比较的是写入量、局部性、分支、算术、对象体积和接口成本。

## 当前决策

现有证据不支持继续优化排盘管线：

- 两个构造入口已经保持零堆分配；
- 单盘构造约为 `241–244 ns`，单核吞吐约为 410 万盘每秒；
- 单张 `Natal` 约 `2.1 KiB`，普通单盘使用不构成容量问题；
- 主要候选方案都会改变公开 API、存储语义或领域对象结构，复杂度明显高于当前可证明的收益。

`Decade` 占 `Natal` 体积约 `68%` 只是结构信号，不是已经测得的性能瓶颈。只有出现下列证据之一时，才重新打开优化决策：

- profiling 显示排盘管线占端到端耗时的显著比例；
- 真实工作负载需要同时驻留几十万张命盘；
- 批量构造达到千万级并受到 CPU 或内存带宽限制；
- FFI、序列化或对象搬运明确受 `Natal` 体积限制。

在触发条件出现前，不为下列候选方案创建实施任务。

## 方案一：压缩大限时间结构

### 表示

不再为每个大限预先保存十个 `DecadeYear`，而是保存生成这些事实所需的最小参数：

```text
Decade {
    index,
    ming_palace_branch,
    age_start,
    year_start: Option<i32>,
}
```

第 `i` 个年份按值计算：

```text
age = age_start + i
year = year_start.map(|year_start| year_start + i)
```

`Decade::years()` 改为返回有确定长度的只读迭代器或专用 `DecadeYears` 视图，不保留旧数组 API 的兼容层。

### 成本与预期

- 大限构造从写入 120 个年份条目缩减为写入 12 个摘要；
- 单个年份读取仍为 `O(1)`；完整遍历仍是固定十次；
- 每个 `Decade` 预计可由 `124 B` 降至约 `12 B`；
- `[Decade; 12]` 预计可由 `1488 B` 降至约 `144 B`；
- `Natal` 预计可由 `2188 B` 降至约 `844 B`，约减少 `61%`。

以上体积是按当前类型布局估算，必须由实现后的 `size_of` 测量确认。

### 取舍

这是一项公开接口和存储语义变更。当前[领域语义收敛](domain-semantics-convergence.md)明确写明 `DecadeYear` 保存在 `Natal`，当前[公开接口与领域类型](public-interface-and-domain-types.md)也规定聚合数据按借用返回。实施前必须先决定：

- “年份和虚岁是 `Natal` 的固定事实”是否允许用无损生成参数表示；
- `DecadeYear` 是否仍是按值生成的公开结果类型；
- 是否接受 `years()` 从数组借用改为只读迭代器。

如果调用方每次构造后都会立即完整遍历全部 120 个年份，eager 表示可能在读取端更快；因此必须增加完整年份遍历基准，不能只看构造时间。

## 方案二：压缩宫位事实图

该方案面向大量命盘驻留、复制或跨边界传输的场景，分为两个可以独立评估的切片。

### 2A. 压缩四化关系

当前每条 `PalaceTransformation` 独立保存：

- 源宫名与源宫支；
- 四化代码；
- 目标宫名与目标宫支；
- 目标星曜。

在管线内部，源宫由父 `Palace` 决定，四化代码由固定数组下标决定，目标星曜可由源宫干和四化代码决定，目标宫名可由目标宫支定位。因此，最紧凑的物理表示只需要为每条关系保存目标宫支：

```text
[[Branch; 4]; 12]
```

该表示预计可把四化关系从 `288 B` 降至 `48 B`，节省约 `240 B`。

但是，[领域语义收敛](domain-semantics-convergence.md)明确要求 `PalaceTransformation` 保留完整源、目标坐标，以便关系独立校验；[ADR-0003](../adr/0003-fly-edge-model.md)也要求自化在排盘时判定并随事实保存。只存目标支与这些现行决策冲突，除非先修订或取代相应决策，否则不能实施。

### 2B. 紧凑星曜落位

当前每个宫位都预留六颗星的 `ArrayVec` 容量。可选表示有：

1. 全局连续 `[Star; 18]`，另用 13 个偏移量表示十二宫切片；
2. 每宫一个 `u32` 位集表示十八颗固定星曜，再以全局数组保存星曜事实。

两者都能消除大部分未使用的宫位内联容量，理论上可再节省约 `250 B`。

- 如果主要操作是按宫顺序遍历星曜，优先连续数组与偏移量；
- 如果主要操作是成员判断和稀疏遍历，位集更合适；
- 两者都会要求 `Palace` 成为借用 `Natal` 的视图，或改变 `Palace::stars()` 的返回形态。

该方案实现和接口成本明显高于方案一。只有在大量保留命盘、序列化、FFI 或缓存的真实需求出现后才值得实施。

## 方案三：使用小型静态查表

排盘公式的输入域很小，可以把部分计算预生成为只读常量表：

| 计算 | 表维度 | 约占空间 |
| --- | --- | ---: |
| 十四主星落宫 | `5 × 30 × 18` | `2700 B` |
| 四颗辅佐星落宫 | `12 × 12 × 4` | `576 B` |
| 命宫、身宫地支 | `12 × 12 × 2` | `288 B` |

核心表合计约 `3.6 KiB`。运行时以数组寻址代替部分除法、取模、分支和短循环，构造复杂度仍为 `O(1)`，但常数可能下降。

实现时应由现有公式通过 `const fn` 生成常量表，避免手工维护第二份规则。现有公式可能已经被编译器有效展开，而且当前构造很可能受结果写入量影响，因此该方案必须通过 A/B benchmark 证明收益，不能仅凭查表更快的直觉采用。

## 条件性方案

以下方案不进入 `ziwei_core` 默认构造路径：

- **批量并行**：只在外层对大批独立输入分块并行；单盘约 240 ns，不在十二宫或十八星内部创建并行任务。
- **应用层缓存**：只在业务层确认同一输入高频重复时使用有界缓存并复用共享结果。`ZiweiInput` 有 518,400 种合法组合，按当前 `Natal` 体积完整缓存仅裸数据就约 `1.06 GiB`，不适合进入 core。
- **编译配置优化**：固定部署目标可以单独评估 ThinLTO、PGO 或目标 CPU 优化；这些属于最终二进制策略，不改变领域模型。
- **手写 `MaybeUninit` 或位级打包**：当前字段枚举已很紧凑，除非剖析和基准证明安全实现留下显著成本，否则不引入 `unsafe`。

## 触发后的评估顺序

1. 先用真实负载确认瓶颈属于构造延迟、读取延迟、驻留体积还是批量吞吐。
2. 补充读取侧基准：完整遍历大限年份、宫位、星曜和四化关系。
3. 如果瓶颈指向对象写入或体积，把“压缩大限时间结构”作为第一个独立设计切片，先确认存储语义和公开 API，再实现。
4. 重新测量构造延迟、对象体积和读取成本；若算术与分支成为主要成本，再 A/B 验证静态查表。
5. 只有真实场景证明驻留体积仍是瓶颈，才设计紧凑宫位事实图。
6. 并行和缓存留在调用方，依据批量规模和重复率单独决策。

触发优化后，方案一优先的原因是它针对当前最大的已知体积来源，表示简单，且可能同时降低构造写入量和对象搬运成本。方案二只有在内存密度重要时反超；方案三只有在压缩结果结构后，公式计算仍占主要构造成本时反超。

## 正确性约束

任何实现都必须保持：

- 两个构造入口产生相同的本命事实；
- 十二宫顺序、宫名、宫干和宫支不变；
- 十八颗星各落一宫，宫内顺序仍遵循 `StarName::ALL`；
- 每宫固定四条四化，顺序仍为 `Transformation::ALL`；
- 生年四化、自化和来因宫对应关系不变；
- 十二个大限的方向、宫位、起止虚岁和可选农历年序号不变；
- 结果类型仍只能由 core 装配，调用方不能构造非法组合。

## 验证门槛

每个优化切片至少执行：

```bash
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets -- -D warnings
cargo doc --workspace --no-deps
cargo bench -p ziwei_core --bench natal -- --noplot
cargo bench -p ziwei_core --bench natal_allocations
```

并报告：

- Criterion 置信区间，而不只报告单次点估计；
- 两个构造入口的总分配次数和字节数；
- `Natal` 及被修改结果类型的 `size_of`；
- 完整年份、宫位、星曜和四化遍历成本；
- 现有 518,400 个合法 `ZiweiInput` 组合的公开契约穷举结果。

最低验收条件：

- 领域事实和公开不变量完全一致；
- 两个构造入口继续保持零堆分配；
- 目标指标有可重复的实测改善；
- 非目标指标没有无法解释的显著回退；
- 如果改变现行存储语义或公开 API，先更新或取代冲突的设计文档与 ADR，不保留双轨接口。
