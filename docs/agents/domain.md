# 领域文档

工程技能探索代码库时，应按本文件读取和使用仓库的领域文档。

## 工作顺序

新增或修改紫微斗数语义时：

1. 只读梳理当前实现边界。
2. 找出适用的标准或已确认的项目决策。
3. 提出一个边界明确的小决策并等待确认。
4. 确认后实现一个垂直切片，并用测试固定已确认的行为。

规则、术语、历法转换或分析含义尚未确认时，明确指出缺口，不要自行发明行为。

## 探索前读取

- 仓库根目录的 **`CONTEXT.md`**；或者
- 如果根目录存在 **`CONTEXT-MAP.md`**，按其中的指针读取与当前主题相关的各上下文 `CONTEXT.md`。
- **`docs/adr/`**：读取与待处理区域有关的 ADR。多上下文仓库还应检查 `src/<context>/docs/adr/` 中限定于该上下文的决策。

如果这些文件尚不存在，**直接继续**，无需报告缺失，也不要预先建议创建。术语或决策真正得到确认后，再由 `/domain-modeling` 技能按需创建；该技能可通过 `/grill-with-docs` 和 `/improve-codebase-architecture` 进入。

## 文件结构

单上下文仓库（大多数仓库）：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

多上下文仓库（根目录存在 `CONTEXT-MAP.md`）：

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← 系统级决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← 上下文级决策
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 使用术语表中的词汇

在 Issue 标题、重构提案、假设或测试名称中提及领域概念时，使用 `CONTEXT.md` 中定义的术语，避免改用术语表明确排除的同义词。

如果所需概念尚未出现在术语表中，应先判断：这可能是项目并未采用的自创语言，需要重新考虑；也可能是真实的模型缺口，应记录下来交给 `/domain-modeling` 处理。

## 标明 ADR 冲突

如果输出与现有 ADR 冲突，应明确指出冲突，而不是静默覆盖：

> _与 ADR-0007（事件溯源订单）冲突——但值得重新讨论，因为……_
